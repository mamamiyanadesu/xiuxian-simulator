# 《此劫难渡》PRD

状态：首版规格，初始数值待验证。版本：1。

## AI 速读卡

- 产品一句话：寿元将尽的散修，在真假机缘与人情算计中争取结丹。
- 核心循环：观察、调查或选择、收益与征兆、补救或继续、渡劫、复盘。
- 目标平台：手机优先的单人网页游戏，单局目标 5—10 分钟。
- 硬约束：黑色幽默、仙侠底色、后果有因、隐患可补救。
- 推荐默认：预写事件、规则驱动、本地存档，不接实时 AI。
- 发挥空间：人物对白、伏笔、视觉细节及经验证的数值调整。
- P0 验收：三个代表事件、完整游戏循环、存档、通关与失败。
- 最容易翻车：重复结算、刷新重抽、连续事件没有后文。
- 超预期机会：人物记得先前选择，复盘回收具体伏笔。

## 第一章：产品概述

《此劫难渡》是一款文字选择与风险管理小游戏，让碎片时间玩家通过判断机缘、分配资源和处理隐患完成一次筑基冲金丹的修行。

### 1.1 差异化对比表

| 功能 | 参考游戏 | 本产品 | 实现方式 |
|---|---|---|---|
| 风险管理 | 延迟揭晓感染结果 | 有征兆的隐患，可识别并补救 | 隐患状态、来源及补救动作 |
| 进度压力 | 两项数值约束选择 | 修为、寿元、心魔 | 集中规则配置 |
| 故事联系 | 随机对象与结算历史 | 随机遭遇与少量连续故事 | 剧情标记及期限队列 |

参考页面与公开源码已检查。以上只描述观察到的实现，不推断原作者动机。

### 1.2 三类用户画像（设计假设）

| 玩家 | 核心目标 | 需要解决的问题 | 体验重点 |
|---|---|---|---|
| 碎片时间玩家 | 快速完成一局 | 上手和阅读负担 | 短事件、清晰按钮 |
| 故事玩家 | 看有后果的故事 | 随机故事彼此割裂 | 人物返场、伏笔回收 |
| 策略玩家 | 学会规则后表现更好 | 选择与结果无关 | 有效调查、资源取舍 |

上述画像未经玩家调研。已确认难度为初玩会栽、理解线索和补救后明显更容易赢。

### 1.3 可行性边界

| 在范围内 | 排除在外 |
|---|---|
| 筑基冲金丹、原创事件、存档、复盘 | 宗门经营、装备背包、即时战斗、挂机 |
| 单人静态网页、本地保存 | 账号、付费、跨设备同步、实时 AI |
| 公开 GitHub 仓库和版本记录 | 默认公开部署游戏网站 |

### 1.4 约束分层

| 硬约束 | 推荐默认 | 发挥空间 |
|---|---|---|
| 仙侠底色、暗讽现实；主角为无依无靠的散修 | 三个主指标与当前数值配置 | 原创对白、剩余事件细节 |
| 隐患有征兆可补救，随机结果不因重绘改变 | TypeScript 与静态网页 | 通过测试调整具体收益和概率 |
| 先创建仓库，再制作项目 | 手机单栏布局 | 四方向预览选定后的视觉表现 |

## 第三章：核心模块详细设计

### 3.1 遭遇与选择

```text
最后一炉
已见线索：新封口、旧丹签、瓶底红末
「先验药」 「取一瓶」 「包下余药」 「离开」
```

正常流程：生成真实情况 → 等待选择 → 结算锁定 → 展示反馈 → 当前遭遇或下一遭遇。

调查消耗寿元、揭示有效线索并保留当前事件。获取或离开推进遭遇；关闭反馈、查看帮助不消耗寿元。调查不能重复收费，人物声称与已确认事实分别呈现。

状态清单与退出条件：等待选择显示合法选项；结算中禁用输入；反馈显示实际变化，用户继续后退出。独立事件单局不重复，事件池为空时提供静修。

失败路径：修为不够支付成本则禁用并显示缺口；事件条件变化则更新合法选项。行动将耗尽寿元时先明确警告，允许玩家作出最后选择。

依赖关系：读取事件和角色，写入数值、隐患、剧情标记、历史。待决问题：无。

### 3.2 隐患与补救

```text
身体征兆：收功时，右手总慢半拍
「内观查明」 → 经脉暗伤 → 「调息疗伤」
```

三类隐患：丹毒、经脉暗伤、功法缺陷。发生后立即给出征兆，内观确认类型，补救清除指定隐患。静心单独降低心魔。

状态：无征兆 → 有征兆 → 已查明 → 已处理。内观、疗伤保留当前遭遇。同类隐患不叠层，保留首次来源。没有可查内容时禁用内观，没有隐患时不提供无效疗伤。

失败路径：修为不足说明缺口并允许继续获取；寿元不足安全完成补救时显示明确后果，避免误触。

依赖关系：读取隐患及角色，写入治疗、历史及新状态。待决问题：无。

### 3.3 连续故事与终局

```text
受许前辈真气 → 未了约定 → 1—2 个遭遇内出现炉火未熄
                         → 继续 / 归还 / 凭记录交涉
修为达标 → 准备渡劫 → 处理未了约定 → 风险预览 → 渡劫 → 复盘
```

后续事件有期限且优先安排，同时最多一条强制后续。返场读取先前选择，不重写既有事实。等待期按推进遭遇计数，调查和疗伤不推进遭遇计数。

主动渡劫前展示已知风险，若有未了契约，先提供原先约定的履约或退出方式。寿尽或心魔失控直接结束，未完故事在复盘交代。

终局状态：成功结丹、寿尽坐化、心魔失控、渡劫失败。反馈与终局中禁止行动；复盘必须来自真实历史，缺记录视为实现缺陷。

失败路径：条件未达标时解释缺口；渡劫不满足成功条件时按状态说明原因，不执行额外致命随机判定。

依赖关系：读取角色、剧情队列和历史，输出结局及原因。待决问题：无。

## 第四章：超越竞品的差异化功能

### 4.1 可补救风险

参考游戏以延迟揭晓为核心，本作增加处理问题的决策。原作者为何未采用此设计，未知，不作推断。

冒险 → 征兆 → 内观 → 付出代价补救 / 保留隐患渡劫。征兆与病因对应，避免泛化的“感觉不对”。

### 4.2 人物记得选择

首批样稿为最后一炉、前辈的一点小忙、各凭本事。许前辈后续有期限，其他返场条件进入事件池。风险是剧情挤占随机性，以最多一条强制后续限制。

超预期机会：返场对白记得旧事；复盘回收当时可见的伏笔；结局区别主动取舍和未察觉的失误。

### 4.3 数值原型与验证

以下参数是待验证起点，集中配置，不代表已平衡。

| 项目 | 初始值 |
|---|---:|
| 修为 | 40，100 可准备渡劫 |
| 寿元 | 18 |
| 心魔 | 0，100 结束 |
| 四档修为收益 | 6 / 10 / 12 / 22 |
| 对应心魔 | 2 / 5 / 15 / 30 |
| 普通行动、调查、内观 | 1 寿元 |
| 清除一个隐患 | 2 寿元、10 修为 |
| 静心 | 1 寿元、心魔 -20 |
| 渡劫 | 1 寿元 |

四档是事件编写参考，不要求每个事件提供全部四档。特殊行动按事件配置显示并结算成本。退契按实际所受真气记账。保守静修参照最低收益档。

成功条件：渡劫后寿元 >0、修为 ≥100、心魔 <60、无隐患。行动原子结算，先评估寿尽与心魔终止，再处理其他结果；历史保存导致终止的行动。

隐患概率初始内部档位为 0%、10%、30%、60%，由事件事实及行动共同决定。玩家看到线索和风险级别，调查可解锁避险选项。受影响行动的潜在结果在事件生成时确定并保存，UI 不参与抽样。内观不得重抽。

固定种子对比保守、最高收益、按线索选择、冒险后补救四种策略。保守路线不得被设计为必败，理解线索必须带来收益，补救不能无限无成本使用。通过玩法测试与人工试玩调参，不预先承诺通关率。

## 第五章：数据模型

事件记录触发条件、公开线索、隐藏事实、行动、条件分支、后续节点。文案与数值分离。

```jsonc
{
  "version": 1, // 必填，存档结构版本
  "rulesVersion": 1, // 必填，规则版本
  "seed": 12345, // 必填，示例种子
  "rngState": 12345, // 必填，当前随机状态
  "phase": "encounter", // 必填，遭遇、反馈或结束
  "cultivation": 40, // 必填，非负修为
  "life": 18, // 必填，非负剩余寿元
  "heartDemon": 0, // 必填，范围 0—100
  "encounterId": "last_batch", // 必填，当前事件标识
  "encounterState": {}, // 必填，已确定事实和可见线索
  "hazards": [], // 必填，隐患类型、来源、查明状态
  "flags": [], // 必填，已发生剧情事实
  "pendingEvents": [], // 必填，后续及安排期限
  "seenEvents": [], // 必填，本局已出现事件
  "history": [] // 必填，选择、实际变化与原因
}
```

规则层统一返回新状态、数值变化、反馈文本标识与历史。UI 禁止直接扣除资源或抽样。

## 第六章：技术架构

```text
事件/规则配置 → 纯规则计算 → 剧情调度与历史
                      ↓
                  页面渲染 ↔ 本地存档
                      ↓
                浏览器操作与验收
```

| 库名 | 用途 | 为何优于替代方案 | 大致包体积 |
|---|---|---|---|
| TypeScript | 状态/规则类型检查 | 减少事件字段及分支错误 | 非运行时依赖，产物待测 |
| Vite | 本地开发/静态构建 | 小型网页构建工具 | 未知，锁定后测量 |
| 浏览器本地存储 | 当前一局保存 | 无账号同步需求 | 依实际存档大小 |

可替换技术原则：推荐上述静态网页组合，不需要后端或游戏引擎；状态、随机、UI、存档分层不可改变。版本与包体积在安装构建后核实，不预先宣称。

最大风险是文案与结算不符，因此预览、结算和复盘共用行动数据。

## 第七章：交互细节

键盘快捷键使用标准导航、Enter/Space 按钮操作，保留浏览器默认右键菜单，不新设单键游戏操作。按钮触控区域至少 44×44 像素，动效支持减少动态效果，不模糊正文。

无存档显示开始；无隐患显示身体状态，不显示无效疗伤。200ms 内不显示加载动画，结算期间仍防连点。

| 触发条件 | 提示信息 | 恢复操作 |
|---|---|---|
| 存档损坏 | 无法读取存档 | 确认后新局 |
| 版本不兼容 | 旧存档无法继续 | 确认后替换 |
| 本地存储禁用 | 本局无法自动保存 | 内存继续 |
| 无合法事件 | 暂无机缘 | 静修 |
| 快速重复点击 | 不额外弹提示 | 忽略重复操作 |

## 第八章：导出与输出系统

### 支持的输出格式

| 格式 | 使用场景 | 质量选项 | 备注 |
|---|---|---|---|
| 游戏结局页 | 查看结丹或失败结果 | 无 | 原创文字与真实状态 |
| 因果复盘 | 理解选择与后果 | 无 | 来源为历史记录 |
| 本地 JSON 状态 | 刷新恢复当前一局 | 无 | 不做文件导出 |

一次选择 → 完整结算 → 生成反馈与历史 → 保存同一状态 → 允许下一次操作。所有步骤顺序执行，保存失败不重做选择。首版无批量导出、分享图和同步。

## 第九章：开发优先级

- P0：三个代表事件、规则循环、隐患补救、渡劫/失败/重开/存档。交付可玩的验证版本。
- P1：扩至 12 个事件节点（含后续）、连续故事、完整复盘、手机适配、调参。完成后形成第一版。
- P2：更多对白变体、结局表现、分享卡。待扩展。
- P3：额外修行路线、内容扩展工具。待扩展，无商业化安排。

其余事件围绕丹药、功法、洞府和人物交易，按统一格式原创，避免为数量重复内容。

## 第十章：性能指标

| 指标 | 目标 | 测量方法 | 劣化阈值 |
|---|---|---|---|
| 单局时长 | 5—10 分钟 | 至少 5 次完整试玩 | 中位数 <3 或 >12 分钟 |
| 输入至可见反馈 | ≤100ms | 浏览器性能记录 | >200ms |
| 首屏可交互 | ≤2 秒 | 移动网络模拟冷启动 | >3 秒 |
| 手机布局 | 360px 宽可用 | 截图及实际操作 | 内容遮挡/横向溢出 |
| 单局存档 | ≤100KB | 序列化长度 | >300KB |
| 随机复现 | 完全一致 | 同种子同操作比较 | 任意不一致 |

以上为验收目标，尚未实测。

## 第十一章：开发者交接说明

### 实现顺序建议

你应先核实公开仓库已创建，提交本策划与样稿，核对远端后制作界面方向预览，选定方向后实现 P0、P1。以阶段提交和分支 PR 管理后续修改，不默认部署网站。

### 最可能返工的三个决策

- 寿元预算：先用当前配置；保守路线被迫必败或最高收益无需判断时调整。
- 调查价值：调查揭示有效事实或解锁避险；调查无助于选择时改线索和分支。
- 连续故事占比：最多一条强制后续；固定剧情占满多数遭遇时减少链长。

### 严格与灵活

第一至三章定位与行为、第五章数据语义、第七至八章恢复与结算、验收中的因果一致性属于约束。第四章具体数值、第六章工具、视觉细节属于建议，可凭证据调整。

### 已知的未知项

真实试玩时长、策略通关表现、剩余事件阅读质量、依赖构建体积均待实际验证；不能把它们当作已完成结果。

### 验收剧本

1. 验收剧本 1：固定种子完成保守路线，对照每次预览、实际扣除、历史，保存测试输出。
2. 验收剧本 2：冒险、看到征兆、内观、补救、渡劫，对照保留隐患路线，记录不同结局的来源。
3. 验收剧本 3：接受许前辈原契书，确认后续在 1—2 个遭遇内出现，执行退契或履约，检查约定清除。
4. 验收剧本 4：在遭遇、反馈、待续剧情阶段分别刷新，以存档与UI验证不重抽、不重复付费。
5. 验收剧本 5：手机宽度完成一局并快速连点，以截图和状态验证可用、结算唯一、终局不可再行动。
